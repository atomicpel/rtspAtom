# HDMI-энкодеры и минимальная задержка

## Какой протокол выбрать

Задержка «кадр закодирован → кадр на экране оператора», показ по WebRTC. Это замер в CI
(`scripts/e2e.sh` и `scripts/screenshots.mjs`): один кодировщик с часами в кадре отдаёт одну и ту же
картинку всеми способами сразу, браузер снимает экран вместе со своими часами, разницу читает tesseract.

| Как энкодер отдаёт видео | Как добавить в панели | Задержка: медиана (разброс), два прогона CI |
|---|---|---|
| **RTSP-сервер** энкодера | «Забирать по адресу», `rtsp://…`, транспорт TCP | **47–52 мс** (15–69) |
| **RTMP push** | «Энкодер отправляет сам» → адрес RTMP и ключ | **18–46 мс** (18–62) |
| MPEG-TS по UDP (юникаст/мультикаст) | «Забирать по адресу», `udp+mpegts://0.0.0.0:порт` или `udp+mpegts://239.x.x.x:порт` | 77–100 мс (60–101) |
| SRT caller (push) | «Энкодер отправляет сам» → адрес SRT | 185–195 мс (178–212) |
| SRT listener | «Забирать по адресу», `srt://энкодер:порт` | как SRT caller |
| HLS | не используйте | 0,57–0,66 с (у энкодеров обычно 2–10 с) |

К этим цифрам прибавьте собственную задержку энкодера (аппаратный H.264 — обычно 30–150 мс)
и сеть (в локальной сети — единицы миллисекунд).

Один кадр при 30 к/с — 33 мс, так что разница RTSP и RTMP в пределах одного-двух кадров.

**Вывод.** В локальной сети — **RTSP** (если у энкодера есть RTSP-сервер) или **RTMP**. Разницы между ними нет.
SRT добавляет около 0,15 с буфера на сервере даже при минимальной настройке: он нужен только там,
где теряются пакеты (радиоканал, длинная линия). UDP без защиты от потерь и без пароля — только
в изолированном сегменте.

## Настройки энкодера

| Параметр в меню энкодера | Значение | Зачем |
|---|---|---|
| Кодек (Video codec, Encode type) | **H.264** | H.265 по WebRTC показывают не все браузеры — будет HLS с задержкой около 1 с |
| Профиль (Profile) | Main или High | Baseline тоже работает, но хуже по качеству |
| **B-кадры** (B-frames, GOP structure IBP) | **0 / выкл., структура IP** | С B-кадрами WebRTC в браузере дёргается, а задержка растёт на длину группы |
| **Интервал опорных кадров** (GOP, I-frame interval, Keyframe interval) | **равен частоте кадров** (25 при 25 к/с, или 1 с) | Картинка открывается за долю секунды; запасной HLS режет сегменты по опорным кадрам |
| Частота кадров | 25 или 30 | 60 к/с удваивает нагрузку на сеть и браузер на стене из 16 камер |
| Разрешение | 1920×1080 (основной поток), 1280×720 (дополнительный) | Дополнительный — для раскладок 9 и 16 |
| Режим битрейта (Rate control) | **CBR** | VBR даёт всплески на опорных кадрах |
| Битрейт | 4–8 Мбит/с для 1080p, 2–3 Мбит/с для 720p | |
| Low latency / Zero latency / Fast encode | **включить** | Энкодер не копит кадры перед отправкой |
| Звук (Audio codec) | **Opus** или **G.711 (PCMA/PCMU)**; не нужен — **выключить** | AAC по WebRTC не передаётся: видео покажется, звука не будет |
| SRT Latency (если используете SRT) | минимум (20 мс) | Итог всё равно не меньше ≈ 0,15 с |
| RTSP: порт / путь | из инструкции энкодера, например `rtsp://IP:554/stream1` | Логин и пароль — в поля панели |
| Сеть | постоянный IP в той же подсети, что и сервер | |

## Настройка в панели

**RTSP-сервер энкодера:** Потоки → Добавить поток → «Забирать по адресу», адрес из инструкции,
логин и пароль, транспорт TCP → «Проверить подключение». Проверка покажет кодеки и предупредит,
если H.265 или звук AAC помешают WebRTC.

**RTMP push:** Потоки → Добавить поток → «Энкодер отправляет сам» → Добавить. Окно покажет:
- адрес сервера `rtmp://<сервер>:1935/live` и ключ потока — в поля «URL» и «Stream key» энкодера;
- или полный адрес `rtmp://<сервер>:1935/live/<ключ>`, если в энкодере одно поле.

**SRT caller:** там же, строка SRT: `srt://<сервер>:8890?streamid=publish:live/<ключ>`; режим SRT в
энкодере — Caller. Если энкодер просит Stream ID отдельно — `publish:live/<ключ>`.

Ключ — пароль на публикацию: без него опубликовать нельзя, а кто его знает, может подменить видео.
Его можно сменить кнопкой «Выдать новый ключ».

**Проверка:** наведите мышь на камеру на видеостене — в правом нижнем углу должно быть «WebRTC».
Значок ⚠ в списке потоков означает, что кодек мешает минимальной задержке (подробность — в подсказке).

## Порты на сервере

| Порт | Протокол | Для чего |
|---|---|---|
| 8080 | TCP | панель |
| 8189 | UDP и TCP | видео WebRTC операторам |
| 1935 | TCP | приём RTMP от энкодеров |
| 8890 | UDP | приём SRT от энкодеров |
| порт из `udp+mpegts://` | UDP | приём MPEG-TS, если используете; установщик его не открывает: `sudo ufw allow 5004/udp` или правило брандмауэра Windows |

Если порт занят, установщик возьмёт следующий свободный и напишет какой; в окне потока адреса
всегда показываются с актуальными портами.
